# Architecture

## Module boundaries

- `src/app` owns application composition and routing.
- `src/components` and `src/pages` contain presentation and browser-interaction orchestration only. They do not own learning, matching, penalty, retry, or persistence rules.
- `src/config` contains centralized application identity and the extensible language registry. Language entries own stable codes, i18n keys, preferred TTS locales, aliases, and neutral preview text; features do not maintain private language lists.
- `src/i18n` owns interface-language resources and initialization. Interface language is independent from Lesson translation languages.
- `src/domain` contains framework-independent models, state machines, validation, randomization, and pure calculations.
- `src/data/database` owns Dexie initialization, persisted record shapes, indexes, and schema versions.
- `src/data/repositories` is the application-facing persistence API. Relationship validation and multi-table deletion are transactional here; `src/data/app-repositories.ts` provides production instances.
- `src/services` adapts browser and desktop capabilities and projects domain/persistence data: audio, downloadable voice/translation packages, local translation inference, image processing/search, Japanese readings, readiness/summary calculation, portability archives, and persistent-storage requests.
- `src/hooks` bridges Dexie live queries and browser state into presentation.

`services/portability.ts` is the only archive boundary. React pages start imports/exports and present localized outcomes, but do not construct manifests, inspect archive paths, validate entities, or write restore tables.

`services/lesson-preparation.ts` is the ordering boundary for offline-ready Lessons. It imports or receives a Lesson, prepares/reuses every eligible generated-audio record, and only then asks the filesystem adapter to serialize the `.vtlesson`. Import UI and Lesson detail do not duplicate this ordering rule. The creation wizard commits the Lesson and navigates immediately; Lesson detail then runs this preparation with visible progress, so slow optional TTS cannot make a successfully created Lesson appear lost.

## Domain engines

- `domain/learning` is the Learn state machine. Its state is composed only of serializable primitives and arrays. Every answer returns a new state, UI feedback metadata, statistics deltas, and any newly Learned Card ids.
- `domain/statistics-engine` defines statistics deltas and applies them without storage concerns. Errors are recorded immediately; completed-question count and response time are recorded only when a question ends correctly or through Give up. `StatisticsRepository.applyDeltas` and `LearnSessionRepository.commitTransition` merge into the same global Card record, so Learn, Quick Choice, and Chaos are cumulative; `StatisticsRepository.reset` is the only ordinary UI path that removes those records and never changes Lesson progress.
- `domain/quick-choice` owns mode, finite/endless length, shuffled Card decks, question state, answer handling, and timing.
- `domain/custom-training` owns the five configurable Practice Builder exercise formats, the derived Card-by-format question plan, ordered or shuffled decks, choice/typing validation, timing, and statistics deltas. React only selects source snapshots and renders the returned question.
- `domain/training-selection` owns composable quick-selection union semantics, manual include/exclude precedence, accuracy filtering, and the exact rolling 30-day error boundary.
- `domain/chaos` owns round layouts, selections, matches, completion, pair timing, and round timing.
- `domain/typing` and `domain/ime` own exact-answer normalization and composition-safe submit decisions.
- `domain/practice` contains shared exercise types, deterministic shuffle support, and unique visible-option generation.
- `domain/srs` is the sole adapter around `ts-fsrs`. It converts Date-based scheduler state into serializable global Card records and owns rating and interval-preview transitions. `domain/today` owns due ordering and the dynamic daily new-card limit.

Engines consume lightweight `PracticeCard` snapshots (`id`, target, selected visible meanings) rather than Dexie entities. `services/lesson-data.ts` deterministically combines all Lesson-visible translations into one meaning value, while React renders the same values with language labels. A caller may provide `meaningOptionKey` to represent the rendered image-plus-translations identity when generating unique Meaning Block options.

The UI builds snapshots through `services/lesson-data.ts`. Learn pages persist returned transitions through `LearnSessionRepository.commitTransition`; Quick Choice and Chaos apply emitted deltas through `StatisticsRepository`. React components never reproduce batch, dirty-card, retry, penalty, matching, or option-generation behavior.

`TrainingPage` may project several same-target-language Lessons into one deduplicated list of `{Card, Lesson}` presentation contexts. Quick toggles and manual checkboxes resolve through one derived Card-id set, so displayed selection and session input cannot diverge. This is not a temporary persisted Lesson: the engine receives only `PracticeCard` snapshots. Explicit “create Lesson from selected” reuses the global Card ids through `LessonRepository.addCard`, preserving the many-to-many model.

`GlobalCardStatistics.lastErrorAt` is optional for backward compatibility and is updated by the shared statistics engine whenever an error delta is applied. This makes the recent-error filter mode-independent without introducing an answer-history table.

`CardStudyMarker` is a separate global Card-keyed record because personal difficulty is explicit user intent, not an inference from lifetime errors or Lesson progress. Home automatic collections are live projections grouped by target language; they never persist duplicate Lessons or Cards. Full backup includes markers, while shareable Lesson packages intentionally do not include this personal state.

`SrsCardState` is global and Card-keyed. A shared Card has one memory state regardless of how many Lessons contain it. The manual difficult marker never mutates FSRS stability, difficulty, or due date. `services/today.ts` projects due reviews and new Cards in Lesson/membership order; React renders the projection but does not calculate workload policy.

Random sources and clocks are dependencies of engine entry points. Production defaults to `Math.random`/`Date.now`; tests inject deterministic functions.

## Persisted relationships

`Card` and `Lesson` are independent global entities. `LessonMembership` is a many-to-many join with compound primary key `[lessonId+cardId]`; adding the same Card twice to one Lesson is idempotent.

`LessonProgress` uses the same compound identity and is created when a membership is created. Removing a membership removes only that Lesson's progress.

`GlobalCardStatistics` uses `cardId` as its primary key. Its lifetime follows the Card rather than a Lesson.

User-authored media blobs are stored as structured Card fields supported natively by IndexedDB. Application-generated speech is stored separately in `generatedTtsAudio`, keyed by Card, provider, voice, normalized source text, and locale, so it cannot be mistaken for higher-priority `customAudio`. Portable formats are ZIP containers with a versioned `manifest.json`; image/audio bytes are extracted to separate asset entries and are never encoded as base64 JSON.

Lesson packages contain Lesson metadata, ordered global Card content, translations, image attribution, custom audio, and compatible generated TTS audio as binary assets. They intentionally contain no progress, Learn sessions, or statistics. Import creates clean per-Lesson progress and reuses an existing normalized global Card when one is already present; existing local global statistics are never overwritten by another user's package.

Full backup manifests contain Cards, Lessons, memberships, per-Lesson progress, global statistics, settings, Learn sessions, SRS Card states and review logs, generated TTS records, and the Dexie schema version. Restore validates format/schema versions, entity values, uniqueness, relationships, Learn-session Card scope, SRS Card scope, generated-audio Card scope, asset paths, and size limits before opening one read-write replacement transaction. A transaction failure rolls back to the prior database. The machine-specific selected-directory handle is deliberately excluded from backup and survives a restore on the current device.

Lesson readiness is a shared service projection. A Card must have every translation selected in `visibleTranslationLanguages` and a valid audio path: Card custom audio, a matching system voice, or an explicitly enabled application provider. `activeTranslationLanguage` is an internal compatibility field derived from the first visible language and has no separate product control. Images are optional and never enter the readiness result. Review and practice routes use the same projection.

`Lesson.contentType` selects vocabulary or symbol interaction without duplicating global Cards. Symbol authoring is a four-step handwriting flow and does not expose vocabulary-only translation selection or entry. The existing Lesson schema still receives one automatically selected compatibility language; kana uses its local reading as the cue, while another script uses the symbol itself so a generic handwriting Lesson remains usable without language-specific logic. `PracticeCard.isKanaStudy` remains a derived presentation hint for vocabulary Lessons, while `requiresHandwriting` is derived from the Lesson. Older all-kana Lessons are recognized as Symbols at the service boundary. Learn, Today, custom-training and the dedicated Handwriting practice route render the shared multi-stroke pointer/touch canvas. Drawing and font-rendered reference points are normalized before a pure comparison combines tolerant bidirectional contour coverage, coarse spatial distribution, proportions and ink density. The comparison deliberately favors a recognizable overall structure over reproducing the typeface, while minimum coverage, structure and proportion still prevent one aligned fragment from passing as a complete sign. The dedicated session engine shuffles Cards, enforces one explicit learner decision per Card and emits ordinary global-statistics deltas without changing Learn or SRS state. The original drawing and reference remain visible together, and the learner can override every provisional visual result. This is deliberately not presented as OCR or stroke-order recognition.

Japanese kana vocabulary also derives `PracticeCard.acceptedTypingAnswers` from the Card target or its saved kana `pronunciationText`. The shared typing domain accepts either the exact target or exact Hepburn romaji, so `じ/ぢ` share `ji` and `ず/づ` share `zu` without depending on IME conversion rules. Non-Japanese Cards and Japanese Cards without a known kana reading keep target-only validation.

## Browser capabilities

Learn alone may pass a target glyph to the shared handwriting canvas as a removable tracing outline; assessment modes never pass this guide. Symbol practice snapshots group normalized identical meanings and carry their complete accepted target set. Domain engines avoid ambiguous reverse choices, while drawing comparison scores every accepted target and uses the best match. Correcting a completed “I do not know” attempt uses a dedicated statistics delta that replaces its error with a correct result without duplicating completion count or response time.

- `config/languages.ts` is the canonical registry for both translation-language availability and UI-locale coverage. `i18n/resources.ts` maps one complete catalog per registry code without locale inheritance. Interface language remains a separate persisted preference; only a fresh settings record derives it from the OS locale, with English as the unsupported-locale fallback.
- All image sources converge on one optimizer: maximum dimension 1024 px, PNG remains PNG so transparency survives, and other compatible images become WebP. Upload, drag/drop, the explicit clipboard button, and safe Card-editor paste use this path; paste events from text-editing controls are ignored. Desktop clipboard reads use a narrow image-only preload IPC while the browser uses Async Clipboard and paste events. Clipboard images carry no invented attribution.
- Google Images is a user-driven discovery workflow, not a scraped data provider. The default query combines meaning and target with picture-dictionary/vocabulary-card terms and requests illustration results; if the learner explicitly includes a photographic style, the style is respected without automatic educational refinements. Desktop opens the ordinary Google Images page in a sandboxed child `BrowserWindow` with Node integration disabled. The supported Electron context-menu event supplies the user-selected image URL; the main process validates and downloads only that image, and the Card stores the available source URL without inventing author/license data. Browser/PWA builds retain the external-browser fallback. Wikimedia search and its adapter were removed.
- Audio playback uses one provider boundary with strict source priority: custom Blob, matching system voice, configured application fallback, unavailable. The generic selector rejects voices whose language does not match the language registry locale. `src/services/tts/providers` contains provider-specific adapters; the Japanese Kokoro/Open JTalk adapter and its dependencies are dynamically imported only when synthesis is needed. The Japanese model/runtime is not part of `dist` or the desktop installer: a narrow Electron IPC boundary downloads it with five pinned voice files atomically into `Vocabulary Trainer Data/tts-packages/kokoro-jp`, reports progress, exposes installed status, and deletes only that validated package directory. Provider IDs include the selected voice while the old provider-only ID remains readable as Alpha. The custom protocol serves installed assets from this portable data directory; provider configuration disables remote models during synthesis and enables ONNX Runtime's WASM proxy with a bounded thread count so initialization and inference run outside the renderer thread. Lesson creation pre-generates application-provider audio sequentially, reports progress, and stores each result in IndexedDB; the shared provider engine promise prevents one model instance per Card. Playback reuses the stored Blob and synthesizes/saves on demand only after a miss. Starting playback cancels prior audio/speech. MediaRecorder and file upload create the same `CustomAudio` value.
- `services/lesson-library.ts` keeps the legacy/browser filesystem adapter and schema-v6 directory handles readable for compatibility, but ordinary Settings no longer asks the user to select a folder. Browser data remains in IndexedDB with manual Lesson export; desktop replaces the adapter with automatic native writes.
- `desktop/main.cjs` and `desktop/preload.cjs` provide the Windows Electron boundary. The renderer is sandboxed with context isolation and Node integration disabled. A standard/secure `vocabulary-trainer://` protocol serves the same built assets and preserves routing, IndexedDB, fetch, workers, and media streaming. Packaged builds set Chromium `userData` to `Vocabulary Trainer Data` beside the distribution before the renderer starts, so IndexedDB, Cache Storage and other origin files move with the application. A narrow preload bridge exposes validated Lesson writes, optional voice/translation-package management, storage information, theme synchronization, and graceful exit.
- On first portable launch, an empty portable root receives a non-destructive copy of an existing Electron profile when that profile contains IndexedDB or related Chromium storage. The old profile is retained. If the distribution directory is not writable, Electron continues with the legacy OS profile and Settings displays the fallback and error.
- The React/Vite build is the shared renderer, not a legacy copy. Electron consumes `dist`, and a future Capacitor Android wrapper would consume the same UI, engines, repositories, media services, and static voice assets.
- `useVoices` and `useAudioAvailability` subscribe to late `voiceschanged` events, so readiness updates when browsers populate their asynchronous voice inventory.
- Automatic translation uses a provider boundary. The production desktop provider is Transformers.js with remote-model access disabled and one pinned, MIT-licensed M2M100 package stored at `Vocabulary Trainer Data/translation-models/multilingual-v1`. It supports every direction between the ten canonical application languages. Package registration validates the manifest and exact size of every file. The provider caches the shared model, passes source/target language codes per request, and exposes separate model-ready and translation-progress signals. Generation is batched, greedily decoded, capped from the input length, and protected against repeated n-grams; the result boundary rejects empty output, removes a trailing hallucinated foreign script, and collapses consecutive repeated tokens. ONNX Runtime's supported WASM proxy executes model initialization and inference outside the renderer main thread so the desktop window remains responsive during the large model's first load and translation. Model loading and each translation batch have user-visible timeouts; Transformers.js interruption criteria stop overlong decoding. A Japanese kana study symbol or contracted syllable has no semantic translation, so it receives a deterministic local Hepburn reading without loading M2M100. Lesson generation and opening an older Lesson both fill missing selected translations for those Cards while preserving manually entered values; longer kana words still use semantic translation.
- Japanese readings are a presentation-only projection. When enabled, `TargetText` emits semantic ruby markup for Japanese Cards containing kanji. A saved `pronunciationText` remains authoritative; otherwise a lazy, bundled Kuromoji dictionary generates a hiragana reading locally. Typing/domain data is unchanged.
- Storage persistence is best effort. The first suitable save calls `navigator.storage.persist()` once. Desktop Settings reports the actual portable directory size and filesystem free space instead of presenting Chromium's origin quota as an application limit. Missing or rejected browser persistence APIs do not block local saves or backup.
- Vite PWA generates the manifest and Workbox service worker. The application shell, hashed route chunks, and compressed Japanese dictionary are precached; user data and media remain in IndexedDB. Local translation is available only through installed desktop packages.

## Database and migrations

`VocabularyTrainerDatabase` accepts a database name so tests use isolated disposable databases. Production uses the centralized default name.

Schema changes are appended as new `version(n).stores(...).upgrade(...)` declarations. Existing versions are never edited after release. Schema version 1 defines Cards, Lessons, memberships, progress, global statistics, and application settings. Version 2 adds serialized Learn sessions. Version 3 adds hydrated language/image/audio Settings defaults and a per-Lesson `useImages` preference. Version 4 adds default and per-Lesson visible translation lists, migrating old records to their active translation without changing store keys or discarding data. Version 5 adds the derived `generatedTtsAudio` store. Version 6 adds machine-local filesystem handles; existing data requires no destructive migration.

Version 7 adds the global `showJapaneseReadings` preference with a non-destructive `false` default. Fresh settings now default to dark theme and system-locale interface detection; existing theme and interface-language values are preserved.

Version 8 adds the global `cardStudyMarkers` store. Existing Cards remain unmarked and all prior data is preserved.

Version 9 adds global `srsCards` and append-only `srsReviewLogs`, plus the daily-new-card preference. Existing Learned Cards are migrated as immediately due without changing Lesson progress, Cards, statistics, or manual difficult markers.

Correct-answer feedback is immediate and remains visible until the user explicitly selects Next or presses Enter. Persistence and audio start without advancing the visual question. The visible timer freezes from the completed statistics delta, and the typing field stops propagation of its submit Enter so that one physical keypress cannot also advance. `resumeLearnSession`/`resumeQuickChoiceSession` then reset the next question timer, so review time is not counted as response time and slow audio is never on the navigation critical path.

All exercise engines expose an explicit unknown-answer transition. Learn marks the Card dirty and schedules its return; the other finite-question modes record one error plus one completed question. A rejected answer can be manually corrected from the exact pre-answer engine snapshot held by the page. The persisted rejected error deltas are compensated before the correct completion delta is applied, so only the latest rejection is reversed; earlier errors and their engine consequences remain. Chaos tracks completed word-side and meaning-side items independently so a manually accepted cross-pair cannot disable unrelated buttons.

`PracticeViewport` measures the remaining viewport below each practice header and scales only an oversized active question panel. Shared keyboard helpers reject editable targets/modifiers and map visible `1`–`4` badges to option indexes in Learn and Quick Choice.

Restarting Learn uses `LearnSessionRepository.restartLesson`. One Dexie transaction deletes previous sessions, clears only the selected Lesson's progress/temporary state, and stores the new all-Card session. Global statistics remain untouched.

`LearnSessionRepository.commitTransition` atomically persists a Learn transition across the session record, `LessonProgress`, global Card statistics, and first-time FSRS graduation. This is the persistence boundary future UI code should call after each answer.

## Testing boundary

Pure formulas and all engine state transitions use unit tests. Repository contracts, version migration, atomic learning commits, Lesson packages, and backup rollback/round-trips run against disposable `fake-indexeddb` databases. React Testing Library covers the shell and Lesson authoring/review integration. Playwright runs against `vite preview` so E2E exercises the generated service worker, real IndexedDB, complete Learn/Automate portability workflow, and offline app shell rather than dev-server behavior.
